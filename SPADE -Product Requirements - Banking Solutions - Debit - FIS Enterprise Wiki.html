    Business Overview and Objective

    Overview

    Spade offers a real-time transaction enrichment API that transforms messy transaction strings into clear, actionable and structured merchant data. Their service returns merchant names, logos, spending categories, geolocations and more all sourced from a proprietary "Ground truth" dataset, delivering results in under 50 milliseconds.

    Few standouts feature that Spade promotes as part of their value proposition:

    • Ground-Truth Data: Unlike solutions relying on guesses or scraped data, Spade uses a proprietary data network that covers almost 100 % of U.S Merchants

    • Speed & Performance: The API responds with enriched data in under 50ms

    • Rich Enrichment: Beyond names and logos, Spade provides accurate categories, geospatial data (latitude/longitude), consistent merchant IDs and more.

    • Deep Coverage: Claims of covering >99.9% of U.S merchants ranging from national chains to small local businesses

    • Secure and Auditable: Built to be fact-based and transparent, not a black box, with SOC 2 certification and real data backing it.

    Problem Statement

    As an issuer processor, we encounter daily challenges caused by messy and cryptic transaction data. These issues lead to:

    • Misfiring fraud models due to unclear or inconsistent merchant information, increasing false positives and missed fraud cases.
    • Frustrated customers confused by vague transaction descriptions, leading to higher call center volumes and disputes.
    • Delayed dispute resolution, since unclear merchant or transaction details make it harder to verify claims.
    • Challenges in customer support, where agents struggle to explain transactions without clear context, impacting service quality.
    • Difficulty in analytics and reporting, as poor data quality limits insights into customer behavior and merchant performance.
    • Increased compliance risk, as unclear data can hinder accurate reporting and audit trails.
    • Operational inefficiencies in reconciliation and settlement processes due to mismatched or incomplete transaction metadata.
    • Reduced trust in digital banking, when customers feel uncertain about their transaction history.

    Why Is Transaction Data So Messy?

    In the payments value chain—spanning issuing banks, payment gateways, processors, card networks, acquiring banks, and merchants—the ISO 8583 standard governs the structure of transaction messages. While it ensures consistency across systems, it also introduces significant limitations that contribute to messy and cryptic data:

    • Truncated Data: Merchant names and locations are cut off due to strict character limits in ISO 8583.
    • Inconsistent Formats: Each network uses custom fields, creating formatting inconsistencies.
    • Lost Context: Valuable transaction details are stripped as data moves through the payment chain.
    • Outdated Systems: Legacy infrastructure can't handle modern payment types or rich data.
    • Complex Messaging: Bitmap-based ISO 8583 messages are rigid and hard to interpret.
    • Digital Mismatch: The standard was built for physical card use, not digital-first payments like Contactless-payments and Mobile Wallets. 
    • Fragmented Ownership: No single party sees the full transaction picture, leading to incomplete data.

    By the time the transaction reaches issuer, it’s often unrecognizable.

    Few Examples:

    • A coffee purchase at Starbucks may appear as “MGRSBUX 53846 10001 NEW YO”

    • All Amazon purchases are labeled as “Book Stores” due to outdated MCC codes

    • Spade identified over 65,000 unique descriptors for Walmart transactions in just three months. Some of the most common ones include:

      • WAL-MART #4262
      • WM SUPERCENTER #2358
      • WMT SUPRCTR #1095
      • WMT PLUS

    More examples: https://blog.spade.com/

    Use Cases

    Merchant Enrichment

    • Replace vague or cryptic merchant names with clean, recognizable names and logos.

    • Provide merchant location, website, and contact info to improve transparency.

    Risk insights for a Transaction

    • Irregular, Negative web sentiment, High Risk entity, Risky industries and Card Acceptance History

    Enhanced Transaction Information (Call center support)

    • Spending Channels (Digital/Physical)

    • Third Parties (Intermediary involved in a transaction: Example: Paypal, Venmo)

    • Transaction Recurrence Information

    Enhanced Transaction Categorization (If banks want to use enriched data in their Mobile apps to enhance cardholder experience )

    • Automatically classify transactions into categories like groceries, dining, travel, subscriptions, etc.

    • Improve budgeting tools and financial dashboards for end users.

    Fraud Detection & Alerts

    • Detect anomalies in transaction patterns or merchant behavior.

    • Flag suspicious transactions based on enriched metadata.

    Product Requirements

    Spade 1.0

    Transaction types 

    MTI

    Transaction Types

    Auth Request (0100) and   Financial Transaction Request (0200)

    Purchase, Purchase with cashback, and Refund

    Connex
    • Connex to identify spade eligible transactions using BIN configuration and establish a real-time integration with Spade for enriched data. 
    • Connex to support the following delivery channels for Spade 1.0: 
      • Send the Spade enriched data to Data navigator (FINIPC message to have a new segment # token for Spade)
      • Support real time integration to send enriched data in ISO message. (GUID for PIB24F)
      • Send Spade enriched data to Fraud Navigator (The Spade enriched data will be added by default in FINIPC and FN will ignore the Spade data for now)
        • Regression testing with FN
    • To address the enrichment data size issue, Connex will enforce a 3,910-byte message size threshold.
    • If Spade enrichment causes the message to exceed this limit, the Spade Interface will remove certain data elements: TransactionInfo.atmInfo, transactionInfo.recurrenceInfo, and mobileAppInfo.
    • If the message still exceeds the threshold, the Spade Interface will retain only the essential merchant and location fields: counterparty, counterparty.industry, and counterparty.location.
    Data Navigator to support the below delivery channels for Spade 1.0

         a. DN UI:

    • Enriched Spade data should be displayed in a separate tab within DN transaction details.

    • Access to enriched data will be subscription-based, possibly at institution and/or user level.

    • DN must support role-based access control to manage visibility of this separate tab.

    • Existing DN data will not be overwritten. The enriched data should be distinct and clearly labeled. 

         b. Transaction Activity: 

    • The Transaction Activity (TXNACT) file will include the Spade GUID for all supported transaction types listed above.
    • Only the GUID will be included in the TXNACT file. The full Spade enriched data will not be stored in this file.

         c. XLTRAN API and DX table: 

    • Enhance the DN transaction details API (XLTRAN API) to include Spade-enriched data, retrievable by GUID for use by P1UI and Code Connect. 
    • Add Spade-enriched data into the DX table to ensure it is indexed and accessible via Elastic Search.
     P1UI
    • Spade enriched data should be displayed in P1UI Card overview→ Transactions→ Transaction Detail Information in a separate section. 
    • IDP permissions should control the institution and user access to view the Spade data
    • Spade-enriched data should be indexed in Elasticsearch from day one to avoid significant rework later, as retroactively pulling data from DN would require considerable effort
     Code Connect
    • Code Connect API to support the delivery of Spade enriched data by GUID to:  
      • Code Connect API clients
     Card base (PIB24F to be supported)
    •  CMSe UI: 
      • Spade enriched data should be displayed in CMSe UI. 
      • UI placement: A link will be displayed on the Transaction Details page. When clicked, it will open a modal presenting the Spade enriched data to the user.
      • CMS security & Prefix parameter to handle access at the institution and user level. 
    •  Card base API support
      • Card base to get Spade data from the Code Connect Spade API
    • Datamart:
      • Spade GUID will be integrated into Datamart files for supported transaction types. The full Spade enriched data will not be stored in Datamart.
      • Access to enriched data will be enabled via GUID-based queries. (Tech design to analyze any storage or field space concerns related to GUID integration.)
     Categorization of Spade Data in DN, P1UI and CMSe UI: 

    • Transaction Info:

      • Transaction Type, Sub type, Name, Category name, Graphic and Graphic source.

      • Transaction ID, Transaction recurrence, Transaction Interval days, Next payment expected and Recent recurrences

    • Third Parties (Intermediary involved in a transaction)

      • Id, Name, Type, Logo and Website

    • Spending Info:

      • Channel

    • Transfer info:

      • Transfer direction, Adjustment or refund (True/False)

    • Risk Insights:

      • Irregular web presence detected

      • Negative online sentiment

      • High risk entity

      • Risk Industry

      • Card acceptance history

    • Counter Party: (Cleansed Merchant information)

      • ID, Name, Legal Name, Industry ID, Industry name, Industry Icon, Match score

      • Counter Party location Id, Address, Address line 1, Address line 2, City, Region, Country, Postal Code, latitude, Longitude, Phone Number & Match score

      • Logo, Phone number, Website, Possible counter party alternate ID and Similarity score

      Monitoring and Alerting (SLAs to be defined)

    Scenario

    SLAs agreed with Spade 

    Connex did not receive a card enrichment API response from Spade and times out in X ms to proceed with auth processing without Spade enriched data

    • After X consecutive timeout FIS should send an email alert to Spade and to FIS proc ops team.  
    • Need to define escalation process  
    Monitor overall response rate
    • FIS to monitor percentage of Spade response for the last X minutes/Hours. Set a threshold % and notify Spade and FIS proc ops. 
     Spade API specification
    • As part of the initial agreement FIS will be utilizing "Card enrichment" API from Spade. 
    • https://docs.spade.com/api-reference/card-enrichment/enrich-a-card-transaction


    Spade 2.0

     1. The below delivery channels will be supported based on specific client requests. 

    • Event-Based Delivery: Clients can subscribe to event brokers (e.g., webhooks) to receive enhanced data automatically when transactions occur.

    • API access: Clients can retrieve enriched data via APIs—either immediately after a transaction or when needed (e.g., for mobile apps or statements).

    • DDS: A solution to enable, Data & Decisioning solution (DDS) team to extract enhanced data efficiently. This capability should support external monetization efforts, including data sales to financial institutions like Bloomberg.

    • Ethos:

    • DN posting files: Spade enriched data will be added to DN posting files based on a specific request from clients. 

    2. Billing/Revenue model (Still under discussion)

    • Enterprise License: Includes monthly base billing plus additional per-user license fees for accessing Spade data via DN, PIUI, and CMSE UI.
    • API Clients: Charged based on a base subscription plus a per-transaction usage fee

    3. Spade-enriched data for Reversal Requests (0420), Authorization Advice (0120), and Financial Advice (0220) will be provided with DN performing the matching against the original authorization. This functionality will be implemented only upon specific client requests. 

    Dependencies

    External Dependency
    • Connex is dependent on Spade to provide the enriched data. 
    Internal Dependency
    • Data Navigator: Depends on the availability of Spade-enriched data in the FINIPC message.
    • PIUI & Code Connect: Depend on the availability of Spade-enriched data in XLTRANAPI.
    • Elastic Search Implementation: Depends on Spade data availability in DX_DATA.
    • Card base (CMSE UI, API, and Datamart): Depends on the implementation of Spade GUID in Code Connect

    Out of Scope

    • Connex will not retry the API requests to Spade in case of timeout or 5xxx error responses.
    • ATM transactions are excluded. 
    • Falcon team is not willing to use the Spade data. Hence no interface changes are needed from Connex to send the Spade enriched data to falcon.
    • Support fraud-related use cases leveraging Card Suite, Falcon & Fraud Navigator
    • Connex or DN matching reversals and advice with original authorization data to enrich Spade data
    • Providing Spade enriched data in IBS vertical stack file is out of scope. 
    • Denied transactions are out of scope for Spade enriched data
